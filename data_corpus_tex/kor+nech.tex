\section{Введение}

\vspace*{-2pt}

  Стремительный прогресс компьютерных технологий, программных средств и~взрывное развитие глобального информационного пространства, возникшего с~появлением Интернета, объединившего между собой компьютерные сети во
всемирную систему передачи информации с~помощью
  ин\-фор\-ма\-ци\-он\-но-вы\-чис\-ли\-тель\-ных ресурсов,~--- все это ознаменовало
вступление человечества в~новую эру больших данных (Big Data). В~качестве
одного из наиболее впечатляющих примеров больших данных приводят потоки
экспериментальных данных физики высоких энергий, поступающие с~Большого
адронного коллайдера (БАК) в~ЦЕРНе~[1]. За время первого запуска БАК в~2012~г.\ четыре экспериментальные установки на нем ALICE, ATLAS, CMS и~LHCb выдавали каждую секунду один петабайт (10$^8$~байт) данных.
Запомнить такое количество данных невозможно ни на какой из современных
вычислительных систем. Поэтому после сверхбыстрой сложной электронной
предобработки, оставлявшей только одно полезное физическое событие из
10~тысяч, выполнялся их анализ в~ЦЕРНовском компьютерном центре
обработки из многих тысяч процессоров. После этого анализа оставался только
1\% событий, возможно содержащих искомый физический феномен. Но даже
после такого радикального сокращения потока экспериментальных данных в~миллион раз для этих четырех больших экспериментов требовалось хранить
поступающие в~год 25~петабайт данных в~специальных роботизированных
ленточных хранилищах, так как копии этих данных подлежат передаче в~сотни
физических центров в~36~странах мира для более тщательного анализа на
сотнях тысячах компьютеров, объединенных во Всемирную сеть
распределенных вычислений~--- Worldwide LHC Computing Grid (WLCG).
Ежедневно в~WLCG обрабатываются полтора миллиона заданий, на что одному
даже самому мощному современному компьютеру потребовалось бы 600~лет.
Сравнение БАК по общим объемам перерабатываемых в~2012~г.\ данных с~тем,
что выполняется в~социальных сетях, поисковых системах, разных отраслях
бизнеса, медицины, климатических прогнозов и~др.\ наглядно показывает, что
исследования в~ЦЕРНе идут в~условиях больших данных.

  На торжестве 4 июля 2012~г.\ по поводу получения ЦЕРНом Нобелевской
премии за открытие бозона Хиггса директор ЦЕРНа Рольф Хойер прямо назвал
грид-технологии одним из трех столпов успеха (наряду с~ускорителем LHC
(Large Hadron Collider)
и~физическими установками). Этот успех также подтверждает, что ЦЕРН,
войдя в~эру больших данных,
 является одним из примеров (наряду с~созданием в~ЦЕРНе
WWW~--- Всемирной паутины), когда разработки в~области физики частиц
начинают влиять на исследования в~других научных областях.

  Следует отметить, что в~2015~г.\ предстоит вторичный запуск БАК после его
существенной модернизации, когда поток данных возрастет в~2,5~раза при
удвоении времени на их обработку. В~своих планах на такое развитие
компьютинга в~ЦЕРНе после 2015~г., которое смогло бы обеспечить
потенциально новую физику, помимо значительного увеличения
вычислительных мощностей и~ресурсов хранения данных, совершенствования
программных средств анализа и~моделирования, активного использования
распределенных параллельных вычислений предлагается повысить
эффективность распределенных систем вычислений на базе WLCG путем
синтеза грид и~облачных технологий~[2].

  Такие же планы характерны для ведущих физических центров мира, в~том
числе и~для ОИЯИ.

  Жесткая структура системы грид создавалась для интеграции уже
существующих аппаратных и~программных ресурсов, зафиксированных в~системе, в~то время как облачная структура распределенных вычислений
оказывается более гибкой, используя виртуальные кластеры. Как было
показано в~недавно защищенной в~ОИЯИ диссертации Н.\,А.~Кутовского,
включение в~грид с~его жесткой структурой, ориентированной на интеграцию
уже существующих процессорных и~программных ресурсов, облачных
структур, более гибких за счет использования виртуальных кластеров из
виртуальных вычислителей, позволяет сократить время решения широкого
круга задач в~области физики высоких энергий и~повысить эффективность
использования ресурсов~[3].

  Примером уже имеющейся технологии, реализующей подобный синтез для
работы с~большими данными, является система PanDA (Production and
Distributed Analysis~--- обработка данных и~распределенный анализ)
эксперимента АTLAS на LHC. Сегодня PanDA рассматривается как возможная
система для российского мегапроекта NICA в~Объединенном институте
ядерных исследований (г.~Дубна)~[4].

  Следует подчеркнуть, что в~силу своей сложности и~высокой стоимости
разработка таких сложнейших грид-об\-лач\-ных систем сбора, передачи и~распределенной обработки сверхбольших объемов информации требует
больших предварительных исследований по выбору их оптимальной структуры
с учетом стоимости и~предполагаемых ресурсов и~загрузки. Подобные
исследования должны основываться на тщательном моделировании как потока
заданий с~учетом их типов и~статистических данных о распределении времени
их поступления и~требуемых компьютерных ресурсов для их выполнения, так и~состава моделируемой грид-струк\-туры.

  Настоящая работа посвящена разрабатываемой в~ЛИТ ОИЯИ новой системе
моделирования грид и~облачных сервисов, ориентированной на повышение
эффективности их разработки путем учета качества работы уже
функцио\-ни\-ру\-ющей системы в~прогнозах на ее дальнейшее развитие. Это
предлагается сделать за счет объединения самой программы моделирования с~системой мониторинга реального (или модельного) грид-об\-лач\-но\-го сервиса
через специальную базу данных, осуществляющую сбор и~статистический
анализ по вычислению распределений данных мониторинга, используемых
затем для динамической коррекции параметров моделирования.

решена в~данном случае на основании стандартов, применяемых для отраслевых центров
или ориентированных на определенный сегмент рынка, в~силу нестандартности
задач, которые решает ВЦ. Требуется новый инструмент для анализа

\section{Подход к~моделированию}

  Предлагаемый подход состоит в~имитационном моделировании,
объединенном с~мониторингом процессов прохождения задач и~передачи
данных. Эффективность этой концепции состоит в~том, что техническое
решение проверяется на модели прежде, чем обсуждается его фактическая
реализация. Развернутое обоснование предлагаемого подхода, а~также описание
функций мониторинга, используемых при моделировании, дано в~[10],
поэтому отметим здесь, что модель должна рассматриваться как
неотъемлемая часть системы обработки данных, а~данные мониторинга~--- как
входные для моделирования. Это позволит принимать обоснованные проектные
решения при развитии системы.



  Центральным компонентом такой процедуры принятия решения по развитию
вычислительной установки является имитационная модель вычислительной
структуры, в~которую в~качестве входной поступает информация,
накапливаемая в~ходе мониторинга существующей установки в~специальной
базе данных, где она модифицируется в~соответствии с~планами развития
моделируемой грид-облачной структуры.

  Схема программы SyMSim (Synthesis of Monitorng and Simulation~--- Синтез
Мониторинга и~Моделирования), реализующей идею синтеза процессов
мониторинга и~моделирования, представлена на рис.~1.



\section{Область моделирования}

  Объектами моделирования являются вычислительные установки,
предназначенные для обработки потоков информации объемом до десятков
петабайтов в~год, поступающей с~детекторов, которые производят ускорители
заряженных частиц~--- как существующие LHC-CMS~[11], LHC-Atlas~[12], так
и находящиеся в~процессе создания или проектирования FAIR-PANDA~[13],
BES-III~[14], NICA-MPD~[15]. Как отмечалось выше, опыт мировых
физических экспериментальных центров показывает, что единственно
возможным способом хранения объемов информации, производимых такими
детекторами, является использование роботизированных библиотек. Данные
затем обрабатываются на фермах, включающих тысячи процессоров. Как
правило, структуры обработки данных выполняются в~парадигме грид и~включают в~себя центры с~облачной архитектурой. Специфика данных
заключается в~том, что поток может быть разбит на события, каждое из
которых обрабатывается независимо от остальных.

  Набор программных средств модели создается в~течение нескольких лет.
Если на первом этапе рассматривалось моделирование систем, построенных в~парадигме грид, то в~настоящее время проект сосредоточен на моделировании
облачных структур, интегрированных в~глобальные грид-струк\-туры.

  Как это принято при имитационном моделировании потока дискретных
событий, происходящие в~модели события привязываются к~внутреннему
времени. Результатом работы модели является величина времени обработки
пакета и~понимание того, как структура вычислительной установки
и~производительность отдельных ее частей влияют на это время. Другой вопрос,
на который получают ответ при моделировании: какими резервами обладает
вычислительная установка, т.\,е.\ какова верхняя граница интенсивности потока
задач или данных и~какие компоненты установки оказывают на нее
существенное влияние?

  Объекты модели включают задачи, процессоры, файлы, ленты, дисковые
хранилища, линии передачи данных, роботизированные библиотеки. Список
событий, происходящих с~объектами, включает: поступление задачи в~очередь,
извлечение задачи из очереди, занятие или освобождение вычислительного
ресурса, передачу файла, извлечение ленты из хранилища, ее монтирование,
чте\-ние/за\-пись на ленту и~др. Модель построена в~виде программы имитации
потока дискретных событий на основе библиотеки GridSim~[16].

  Архитектура имитационной модели была адаптирована из
распространяемого по лицензии LGPL (Lesser General Public
License) кода проекта Alea~[17].

  Отличительной особенностью предлагаемой системы моделирования
является ее интеграция с~системами мониторинга вычислительного процесса.
В~частности, используется мониторинг системы запуска заданий PanDA~[18].

пользователь должен указать в~параметрах запуска модели. Модель считывает
информацию из базы и~строит в~памяти описание вычислительной структуры.
Другими данными являются характеристики потока задач, которые подлежат
обработке, и~информация. Блок описания потока заданий~--- набор утилит,
который позволяет статистически проанализировать результаты мониторинга и~сформировать поток заданий, аналогичный или отличающийся от
проанализированного на управляемое воздействие пользователя, в~виде
упорядоченной по времени последовательности записей в~базе данных. Для
обеспечения совместимости с~сис\-те\-ма\-ми мониторинга формат базы данных
был выбран совпадающим с~PanDA~--- сис\-те\-мой управ\-ле\-ния потоком задач
эксперимента Atlas. Такая совместимость дает возможность использовать
результаты мониторинга потока без изменения его параметров.

  Существует множество систем управления, выбор PanDA обусловлен тем,
что эта система в~последнее время рассматривается как перспективная для
нескольких новых или модернизируемых экспериментов. Для того чтобы не
генерировать поток заданий всякий раз, когда необходимо изменить его
интенсивность без измерения распределения типов задач, во входных
параметрах программы определен параметр компрессии потока. На этот
коэффициент умножается <<временн$\acute{\mbox{о}}$е расстояние>> между поступающими в~систему задачами. Аналогичный способ используется для задания
интенсивности потока информации.

\section{Внутренняя структура программы моделирования}

  Ядром модели является планировщик~--- модуль, который в~программе
отвечает за прием заданий на обработку и~<<запуск>> их на процессорах.
Планировщик управляет очередями, сохраняет информацию о~занятых и~свободных в~данный момент процессорах. Текст планировщика заимствован из
проекта Alea с~существенными модификациями и~сокращением функций.

  Другой существенный по объему набор классов описывает миграцию
информации в~системе. Этот набор был создан как расширение библиотеки
GridSim. При его создании авторы отказались от детализации процесса
передачи информации на уровне пакетов в~пользу моделирования
последовательности событий манипуляции с~файлами:
  за\-прос--откры\-тие--пе\-ре\-да\-ча--за\-кры\-тие. При этом
рассчитывается уровень нагрузки на среду передачи, а~не время поступления
пакета на узел.

  Результатом работы программы моделирования служит файл (или
последовательность записей в~базе данных, отражающая все события,
происходящие в~системе). К~ним относится, например, поступление задания,
начало и~конец обработки задания, начало и~конец передачи файла,
манипуляции с~лентами и~т.\,д. Все события описываются в~едином формате.
Запись привязывается к~внутреннему времени.

  По ходу развития проекта из текста модели были удалены все модули сбора
статистики. Необходимость такого подхода выяснилась после того, как авторы
стали анализировать результаты моделирования проекта NICA-MPD~[10, 18].
Поскольку невозможно априори сформулировать весь список параметров,
подлежащих анализу, целесообразно сосредоточиться на получении
информации о событиях, связанных с~прохождением каждого задания через
вычислительную структуру, а~статистические закономерности этого процесса
анализируются и~визуализируются отдельно. В~данном случае для этого были
использованы таблицы Excel. Для большего удобства планируется расширить
проект отдельным модулем, предоставляющим доступ к~результатам
моделирования через веб-ин\-тер\-фейс.

  Перед проектировщиками вычислительных установок естественным образом
встает вопрос, как обеспечить масштабируемость, т.\,е.\ способность установки
сохранять работоспособность при увеличении потоков данных и~задач.
В~SyMSim настройка топологии установки и~характеристик ее узлов
конфигурируется через внешние параметры, что позволяет легко настраивать
модель под различные варианты потоков. Наиболее простой параметр при
настройке~--- это количество счетных узлов. Однако утверждать, что скорость
обработки потока заданий будет линейно зависеть от него, неверно. На
скорость будут оказывать влияние также пропускная способность каналов и~производительность оборудования, на котором хранятся исходные данные.
Возможность учета этих факторов заложена в~SyMSim, но требует дальнейшего
развития. Например, в~программе невозможно учесть деградацию скорости
передачи при увеличении загрузки канала. Поскольку зависимость эта
нелинейная, то вопрос требует расширения функции SyMSim.

  При создании модели надо также обращать внимание на предполагаемый
срок службы оборудования. Например, счетные узлы могут заменяться в~течение нескольких лет, а~роботизированные библиотеки используются
несколько пятилетий. Следовательно, на моделировании процессов в~них
должен быть сделан особый акцент.



  Другая проблема, которая стоит перед разработчиками,~--- это обеспечение
надежности функционирования. Как правило, такие задачи решаются
резервированием оборудования и~моделированием его отказов. В~облачных
структурах вопрос резервирования решается за счет использования механизма
виртуализации, когда процесс может быть перенесен на реплику оборудования
без существенных затрат. В~грид-струк\-ту\-рах для обеспечения
вычислительного процесса используются десятки служб, отказ любой из них
приводит к~невозможности запуска заданий, по крайней мере, от отдельных
виртуальных организаций. Отказ может происходить как по причине сбоя
оборудования, так и~по причине ошибки программного обеспечения. Поэтому в~перспективе в~SyMSim для моделирования грид-струк\-тур необходимо
добавить классы, описывающие грид-служ\-бы как обеспечивающие процесс
вычислений в~целом, и~моделировать отказ этих узлов как
  про\-грам\-мно-ап\-па\-рат\-ный сбой.

  Приведенный пример наглядно демонстрирует, что ширина канала записи

информации. Для более глубокого анализа процессов сбора и~хранения данных
на конкретной установке необходимо проводить заранее спланированные
вычислительные эксперименты. Эта тема выходит далеко за рамки данной
работы.

  Разумеется, невозможно принять решение о конфигурации системы хранения
и обработки данных только на основании вычисленных в~процессе
моделирования параметров. Для оптимального выбора необходимо учитывать
множество факторов, таких как надежность, располагаемые финансовые
ресурсы. Но приведенный пример демонстрирует, как с~помощью SyMSim
можно снять фактор неопределенности, который касается параметров
процессов обработки.

\section{Заключение}

  Разработка грид-облачных систем сбора, передачи и~распределенной
обработки информации требует тщательного моделирования, которое будет
эффективным, только если оно будет учитывать качество работы уже
функционирующей системы в~прогнозах на ее дальнейшее развитие. Новизна
подхода, предложенного авторами, состоит в~соединении процессов
моделирования и~мониторинга в~рамках одного проекта.

  Предложенный подход к~моделированию и~анализу вычислительных
  грид-об\-лач\-ных структур инфраструктуры эксперимента NICA основан на
учете данных мониторинга, используемых затем для динамической коррекции
параметров моделирования.

  Дальнейшее развитие системы предполагает внесение дополнений для
моделирования оригинальных алгоритмов назначения пулов dCache. Структура
моделирующей программы достаточно общая, чтобы в~дальнейшем заменять
упрощения, допущенные на предварительном этапе, на более реальные
условия. Также необходимо провести полномасштабные испытания модели с~целью выявления ее ошибок.
