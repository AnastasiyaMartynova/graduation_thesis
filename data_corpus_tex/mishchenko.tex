\section{Введение}

  В данной статье рассматривается задача поиска уязвимостей в ОС, 
построенной на основе ядра Linux. Сначала проводится анализ современных 
средств автоматизации поиска уязвимостей в ОС с указанием их основных 
возможностей. На этой основе предлагается механизм автоматизации поиска 
уязвимостей в ОС на основе ядра Linux, учитывающий ключевые особенности 
данных систем. Далее подробно описывается математическая модель, 
используемая для ранжирования сервисов анализируемой ОС в порядке 
невозрастания <<уязвимости>>.
  
\section{Обзор современных средств поиска 
уязвимостей в~операционных системах}

  Современные решения как открытые, так и коммерческие, производят 
внешний анализ работающей системы~--- тестирование на проникновение. 
Такой анализ состоит из нескольких этапов:
  \begin{itemize}
\item автоматическое определение доступных сервисов анализируемой 
системы;
\item автоматическая проверка обнаруженных сервисов на наличие 
уязвимостей:
\begin{itemize}
  \item определение версии сервиса;
  \item попытка применения соответствующих версии сервиса 
известных уязвимостей (берутся из открытых или закрытых баз 
уязвимостей).
  \end{itemize}
  \end{itemize}
  
  Также современные анализаторы содержат множество утилит для 
выполнения ручного анализа интересующего сервиса работающей системы. 
    Например, широко известны следующие средства автоматизации поиска 
уязвимостей:
  \begin{itemize}
  \item Metasploit Framework~--- платформа для создания, тестирования и 
использования эксплойтов~[1];
  \item Nessus~--- сканер уязвимостей~[2].
  \end{itemize}
  
  По каждому из указанных средств существует немало описаний их 
использования и внутреннего устройства. Для данной статьи интерес 
представляет то, что указанные средства: 
  \begin{itemize}
  \item  работают по базам известных уязвимостей программного обеспечения (ПО);
  \item во время проведения анализа не учитывают возможность 
доступности процесса разработки компонентов анализируемой ОС;
  \item не предназначены для поиска новых уязвимостей среди множества 
сервисов, находящихся в анализируемой ОС.
  \end{itemize}
  
  Те же самые утверждения распространяются и на другие существующие 
средства комплексного анализа ОС.
  
\section{Внутренний анализ систем, построенных на~базе ядра 
Linux}
  
  Как было отмечено выше, существующие средства анализа уязвимостей ОС 
во время проведения анализа не учитывают важные аспекты 
открытого ПО: открытость исходного кода и разработки компонентов, 
находящихся в анализируемой ОС. На основании этих аспектов можно 
построить автоматизацию поиска новых уязвимостей в системах, состоящих из 
компонентов, для которых доступен процесс их разработки. Для выполнения 
детального анализа систем предлагается следующий механизм:
  \begin{enumerate}[(1)]
  \item сбор статистики обо всех сервисах, находящихся в составе данной 
сборки ОС Linux;
  \item упорядочение всех сервисов системы с использованием собранной 
статистики от наиболее уязвимых к наименее уязвимым;
  \item детальная проверка сервисов ОС в порядке, установленном на 
предыдущем шаге.
  \end{enumerate}
  
  Рассмотрим каждый из этапов более подробно.
  
  \noindent
  \begin{enumerate}[1.]
  \item Для сбора статистики о разработке каждого сервиса используется 
средство автоматизации разбора популярных систем отслеживания ошибок, 
среди которых Bugzilla, Trac, Mantis, Redmine.
  \item Собираемая статистика о разработке отдельного сервиса может 
включать в себя следующую информацию:
  \begin{itemize}
\item объем кодовой базы (КБ);
\item объем изменений КБ (общий объем считается как сумма 
объемов отдельных коммитов);
\item сроки открытия и закрытия каждой уязвимости (с делением по 
важ\-ности~--- критичные, важные и~т.\,п.).
\end{itemize}
  \item Для проведения детальной проверки сервисов выполняется 
следующая последовательность действий:
  \begin{itemize}
\item проверка актуальности версии сервиса (версия в сборке относительно 
последней стабильной версии в репозитории разработки);
\item проверка наличия известных уязвимостей для данной версии сервиса;
\item автоматизация поиска неизвестных уязвимостей данного сервиса:
\begin{itemize}
\item использование статических анализаторов исходного кода для 
данного сервиса;
\item профилирование сервиса во время выполнения;
\item проведение fuzz-тестирования сервиса.
\end{itemize}
\end{itemize}
\end{enumerate}
  
  Стоит упомянуть о существующих подходах к анализу ПО на основе 
информации о его разработке. В~работе~\cite{3-mi} был предложен алгоритм 
FixCache для определения потенциально наиболее уязвимых мест 
разрабатываемого ПО, а в~\cite{4-mi} продемонстрирована эффективность 
данного подхода. В~работе~\cite{5-mi} был предложен алгоритм BugCache. 
Хотя данный алгоритм проще в реализации, чем FixCache, на практике  
качество его анализа оказалось не хуже. Заметим, что в данных работах 
производится анализ одного проекта на предмет потенциально уязвимых мест. 
Однако, расширив описанные подходы, можно реализовать упорядочение 
сервисов ОС по уязвимости (второй пункт предложенного механизма), а также 
использовать их во время анализа конкретного сервиса ОС.
  
  В следующей части статьи будет описана математическая модель, 
использу\-емая для ранжирования по <<уязвимости>> сервисов анализируемой 
ОС.
  
\section{Математическая модель}
  
  Предположим, что набор сервисов анализируемой ОС определен. Обозначим 
его как $\{s_k\}$. Пусть для каждого анализируемого сервиса $s_k$ была 
собрана информация о существующих уязвимостях:
  $$
  \mathrm{bugs}_k=\left\{ \left( i,t_{o_i}, t_{c_i}\right)\right\}\,.
  $$
  
  Таким образом, bug$_k$~--- множество известных уязвимостей 
сервиса~$s_k$. Заметим, что каждая уязвимость описывается тройкой $\left( 
i,t_{o_i}, t_{c_i}\right)$, где $i$~--- порядковый номер уязвимости; 
  $ t_{o_i}$~--- время открытия уязвимости; $ t_{c_i}$~--- время закрытия 
уязвимости.
  
  Для открытых уязвимостей на момент проведения анализа $ t_{c_i}$ 
принимается равным $+\infty$. Обозначим $N_k\hm=\vert \mathrm{bugs}_k\vert$. Тогда 
для множества bugs$_k$ выполняются следующие свойства:
  \begin{gather*}
  \forall i \in \left\{ 1,\ldots , N_k\right\}: \ t_{o_i}<t_{c_ i}\,;\\
  \forall i, j \in \left\{1,\ldots , N_k\right\}, i<j:\  t_{o_i}<t_{o_ j}\,.
  \end{gather*}
  
  Также стоит отметить, что:
  \begin{itemize}
  \item все множества $s_k$ формируются на начальном этапе проведения 
анализа;
  \item для каждого сервиса время нормализуется таким образом, чтобы 0 
соответствовал началу разработки сервиса, а 1~--- времени запуска анализа, 
т.\,е.\ $\forall t_o, t_c\in \mathbb{R}_{[0,\,1]}$.
  \end{itemize}
  
  Далее будут использованы следующие вспомогательные множества и 
функции:
  \begin{itemize}
  \item множество времени: $\mathbb{T}\hm=\mathbb{R}^+ \cup\{0\}$;
\item множество всевозможных наборов уязвимостей: 
$\mathrm{BUGS}\hm=\mathcal{P}(\mathbb{N}\times \mathbb{T}\times \mathbb{T})$. 
Заметим, что $\forall k\in \{1, \ldots ,\vert \{s_k\}\vert \}:\ \mathrm{bugs}_k\in \mathrm{BUGS}$;
\item функция $\mathrm{bugs}\_{\mathrm{at}}:\ \mathrm{BUGS}\times \mathbb{T}\times 
\mathbb{T}\rightarrow \mathrm{BUGS}$, для начального множества уязвимостей и 
временного интервала возвращающая подмножество уязвимостей, которые 
были открытыми в указанное время:
\begin{multline*}
\mathrm{bugs}\_{\mathrm{at}}\left(B,t_{1}, t_{2}\right)= \left\{
(i,t_{o_i}, t_{c_i})\vert 
(i,t_{o_i},  t_{c_{i}})\in 
B\cup t_{c_{i}}\geq t_{1} \cup t_{c_i}\leq t_2\right\}\,,
\end{multline*}
где $B\in \mathrm{BUGS} \cup t_1, t_2\in \mathbb{T}$;
\item множество функций для $\{s_k\}$, возвращающих подмножество 
последних уязвимостей за $\Delta t$ для соответствующего сервиса:
$$
\mathrm{lastbugs}_k(\Delta t) =
\mathrm{bugs}\_{\mathrm{at}}(\mathrm{bugs}_k,1-\Delta t, +\infty)\,.
$$
\end{itemize}

  Теперь можно ввести метрику уязвимости сервиса~$s_k$ за последний 
промежуток времени $\Delta t$:
  $$
  \left\vert s_k\right\vert_{\Delta t} = \sum\limits_{(i,t_{o_i},t_{c_i})\in 
\mathrm{bugs}_k}\left(  \min \left( t_{c_i},\,\max \left( t_{o_i}+\Delta t_c,\,1\right) \right) -
t_{o_i}\right) \fr{1}{1+e^{10(1-t_{c_i})}}\,.
  $$
    Поясним составляющие части данной метрики:
  \begin{itemize}
  \item $\Delta t_c$~--- актуальное среднее время закрытия уязвимости, определяемое как
  $$
  \Delta t_c= \fr{\sum_{(i, t_{o_i},t_{c_i})\in \mathrm{lastbugs}_k(\Delta 
  t_{\mathrm{norm}})} (t_{c_i}-t_{o_i})}{\vert 
\mathrm{lastbugs}_k(\Delta t_{\mathrm{norm}})\vert}\,,
  $$
  где $\Delta t_{\mathrm{norm}}$~--- нормализованное для данного 
сервиса~$\Delta t$;
\item фактическая или предполагаемая продолжительность наличия 
известной уязвимости~$i$:
$$
\min \left( t_{c_i},\,\max \left( t_{o_i}+\Delta t_c,\,1\right)\right)-t_{o_i}\,;
$$
\item вес уязвимости~$i$: $1/(1+e^{10(1-t_{c_i})})$. Данный коэффициент используется для 
понижения вклада давно закрытых уязвимостей в итоговую сумму.
\end{itemize}

  Будем считать, что сервис~$s_i$ менее уязвим, чем сервис~$s_j$ за 
последний промежуток времени $\Delta t$, тогда и только тогда, когда $\vert 
s_i\vert_{\Delta t} \hm\leq \vert s_j\vert_{\Delta t}$. Таким образом можно 
составить список сервисов анализируемой ОС, упорядоченный по 
невозрастанию уязвимости.
  
  Отметим, что в описанной модели нет разделения уязвимостей по их 
<<важности>>. Если в этом есть необходимость, то указанным выше способом 
можно задать вспомогательные метрики для каждого из видов уязвимостей и 
вывести итоговую метрику как комбинацию вспомогательных.
  
  В итоге сформированный упорядоченный список сервисов будет использован 
для третьего этапа механизма, предложенного в третьей части данной статьи.
  
\section{Теоретическая оценка эффективности}
  
  Сравним теоретическую эффективность поиска уязвимости в ОС с 
использованием предложенного алгоритма ранжирования сервисов и без него. 
Предположим, что без использования ранжирования сервисы ОС для анализа 
выбираются случайным способом с равномерным распределением. Заметим, 
что в рамках математической модели невозможно учесть все аспекты 
процедуры поиска уязвимости в ка\-ком-ли\-бо ПО. По\-это\-му будем считать, 
что для любого сервиса из $\{s_k\}$ процедура поиска уязвимости выполняется 
одинаково, и при проведении сравнения эффективности не будем учитывать 
влияние этой процедуры. Условия для сравнения подходов следующие:
  \begin{itemize}
\item время поиска уязвимости в ОС равно~$\Delta t$;
\item при поиске уязвимости в ОС для анализа выбирается один из 
сервисов $\{s_k\}$;
\item результатом проведенного анализа ОС считается результат поиска 
уязвимости в выбранном сервисе.
\end{itemize}

  Определим вероятности нахождения уязвимости в сервисах $\{s_k\}$ за 
промежуток времени~$\Delta t$ как $\{p_k\}$. В~итоге получим следующие 
результаты:
  \begin{enumerate}[1.]
  \item При случайном выборе сервиса для анализа вероятность 
нахождения уязвимости равна  $\sum p_k/n$.
  \item При проведении анализа реальных сервисов было замечено, что 
появление новых известных уязвимостей в них напрямую коррелирует с 
описанным выше понятием <<уязвимости>> сервиса. И так как в данном 
сравнении не учитывается процедура поиска уязвимости, можно считать, 
что $p_k$ тем выше, чем больше значение метрики $\vert s_k\vert\Delta t$. 
Поэтому вероятность нахождения уязвимости при использовании 
ранжирования равна $\max (p_k)$.
\end{enumerate}
  
  Таким образом, получаем, что использование ранжирования повышает 
вероятность обнаружения уязвимости в ОС.
  
\section{Заключение}
  
  В данной статье была рассмотрена задача автоматизации поиска уязвимостей 
в ОС, построенной на базе ядра Linux. Сначала были рассмотрены уже 
существующие средства и показано, что они:
  \begin{itemize}
\item не предназначены для обнаружения новых уязвимостей в ОС;
\item не учитывают доступность процесса разработки анализируемой ОС.
\end{itemize}

  Затем был предложен механизм автоматизации поиска уязвимостей в ОС с 
доступным процессом разработки. После этого была приведена формальная 
математическая модель, описывающая процесс ранжирования сервисов 
анализируемой ОС в порядке невозрастания <<уязвимости>>.
